# Stop conditions

The five terminal states in full. The contract carries the blocked row
verbatim and one line for each of the other four.

## Stop conditions

Five terminal states; pick the first that applies and stop.

- **Homepage blocked.** `homepage-pass-status.json` reports `status: "blocked"` or `blockedBySecurityInterstitial: true`. The packaged pass has already consumed its only eligible residential fallback, or recorded why one was unavailable/ineligible. Write a minimal extraction with `productCard: []` (the schema only permits `evidenceQuality` on `productCardStyle` items, not at the top level), run the finalize step (expect exit 3 — homepage-blocked), and stop. Skip the tone-of-voice and business-context handoffs. No agent-authored page-fix or Browserbase retries, no secondary pages, no tone/business-context/product-card work.
  - **A landed document that is not the page is a block.** `blocker.type: "landed_document_error_status"` means the FINAL main-frame document came back outside 2xx — a 404 for a mistyped path, a 410, an uncleared edge deny. The pass is holding an error page, not the site, and composing from it would REPLACE the account with a kit built from the wrong document. Two things are deliberately different from a security interstitial: `blockedBySecurityInterstitial` is `false` (nothing claimed a challenge), and no residential retry was spent (another egress cannot turn a 404 into a 200). Only the last document to ARRIVE decides — a challenge that CLEARED leaves a 2xx there and is not this state, even when the challenge's own answer was recorded first. Report the status and URL from `blocker.evidence` so the operator can correct the URL. A soft 404 — an error page the server sent with `200` — is NOT covered by this and still composes.
  - **A blank render is a block.** `blocker.type: "blank_render"` means the page answered with no title, no copy, no logo candidate and no link (an anti-bot empty document); the pass has already tried the residential fallback. Treat it exactly as blocked — never compose from it. The finalize blocker says the homepage rendered an empty document; like the landed-document state it does NOT claim a security interstitial, because nothing matched one.
  - **A `homepage-pass-status.json` you cannot read is NOT "not blocked".** The finalize gate fails closed on a corrupt, truncated, oversized, or wrong-shaped status file: it exits **4** with a blocker naming that exact path, not exit 3 and no longer a silent pass — a truncated write from a killed probe can be concealing `{"status": "blocked"}`. If you see that blocker, or if your own `jq` of the file fails, re-run `scripts/homepage-pass.js` to regenerate it. Do not hand-write the file, and do not read an unparseable status as an unblocked homepage.
- **Homepage pass failed.** `wait` reported `failed` or `missing` twice: the pass captured no evidence. Run the finalize step directly, with no scaffold and no extraction, and expect exit 3: it refuses to compose from nothing and writes nothing to the account. Paste its lines and stop. Skip the tone-of-voice and business-context handoffs. The finalizer refuses only when NO probe wrote a row and no logo candidate exists; a pass that died after capturing rows still composes, with the incomplete-pass warning.
- **Recovery budget exhausted.** The bounded probe sequence in [Decision Rules](#decision-rules) ran without resolving a critical field. Accept partial: mark gaps with `missingEvidence`, proceed to normalize. The result will likely surface as `content_warnings` downstream.
- **Non-ecommerce homepage.** No purchase signals anywhere on the page. Use `productCard: []` (empty array — the canonical non-ecom shape); proceed.
- **Normalize retry budget exhausted.** Three `--mode normalize` attempts have run on the same slug without resolution (`BRANDKIT_NORMALIZE_ATTEMPT=3` and high-severity entries remain). **Role-coverage findings no longer reach this state at all** — they carry `severity: "gap"`, the budget gate scans for `severity: "high"`, and the two stopped intersecting. What can still reach it is a `high` entry from another diagnostic array (layout, product-card CTA contract, colour-hint duplication, link-colour alignment). The component-shrinkage gate is the one condition that is fatal on attempts 1-2 and advisory on attempt 3: it counts rows rather than checking truthfulness, blocking early is what makes its repair loop run, and blocking on the last attempt would only guarantee the run saves nothing. Increment `BRANDKIT_NORMALIZE_ATTEMPT` (1 → 2 → 3) before each re-invocation; the attempt counter is surfaced in `assembly-diagnostics.json.normalizeAttempt`. The orchestrator emits a terminal `$.normalizeAttempt` diagnostic and exits non-zero on attempt 3. A `high` that survives three attempts means one of three things: a deterministic producer faulted; or probe provenance could not be proven (a missing or narrowed `text-styles.probed.json`); or the `text-styles.json` capture is itself empty or absent, which is a probe failure rather than an authorship one. Mark the still-unresolved productCard fields with `missingEvidence`, report the surviving `high` entries as a blocker, and stop — do not invoke a fourth normalize.
  - **The carve-out, and where it went.** The budget message still carries an authorized corrective rerun for an `authored_without_evidence` entry, and `parseNormalizeAttempt` still clamps above the cap so that rerun costs one turn and cannot loop. But that entry is `severity: "gap"` now, so on its own it never reaches this diagnostic: a run whose only outstanding finding is a role-coverage one COMPLETES at attempt 3 and persists the kit. The carve-out survives for the shape where an authored role sits beside a genuine `high` from another array — the budget throw then prints the removal repair alongside the surviving blocker instead of contradicting it.
