# Logo flow

Read this when a logo candidate looks incomplete — an empty `url`, an empty
`svgPath`, more than one favicon — or when `finalize-report.json.logo_hosting`
reports an outcome you have to explain. The finalizer's own hosting attempt is
described first, then the authoring rules.

The finalizer owns the one fail-open primary-logo hosting attempt. It matches only the first primary row to this run's `logo-assets.json`; the rest keep their own `url` untouched, because one logo's bytes are not evidence about a different mark. Before any upload-side call it validates the complete sidecar and runs every blocker that is knowable without the future hosted URL; a run refused by that preflight therefore creates no upload session or orphaned asset. It uploads only that validated sidecar, rasterizes it through `prepare_image_upload` / `upload_image`, and writes the exact returned `.png` URL into the in-memory final brandkit. It attempts this for a **raster** primary too — a `.webp` / `.avif` / extensionless URL is not email-safe, so the finalizer converts the captured bytes to a PNG itself and keeps the page's own URL as an `alternative` row; a `.png` / `.jpg` / `.jpeg` / `.gif` URL already works and is left exactly as it is. **Do not call those tools for extraction, do not edit a logo URL after normalize, and do not write `assembly-diagnostics.json.logoHosting`.** Agent-authored diagnostics never authorize a logo fact. Current-run `capture.json`, `page-signals.json`, `logo-assets.json`, and SVG sidecars are cooperative same-workflow evidence for consistency checks, not authenticated provenance; the agent must not edit them, but the filesystem does not enforce that against a deliberate same-UID artifact forgery. That threat is out of scope until a future trusted capture/rehost boundary exists. The exact successful tool result exists only in the finalizer process while its validators run; `finalize-report.json.logo_hosting` records the non-authorizing outcome and reason.
**Logo flow.** Use public source URLs in `brand.logos`. Keep the largest favicon variant when multiple favicons are present.

**The packet pre-selects one primary; copy that row unless you can say why not.** Every packet logo row carries `emailSafeUrl` — `true` when the url is a `.png` / `.jpg` / `.jpeg` / `.gif` an email client renders as stored, `false` when it would need converting first (`.svg`, `.webp`, an extensionless CDN path), `null` when the row has no url to judge — and exactly one `primary` row carries `preselected: true`: highest measured `confidence` first, an email-safe url breaking a tie, the ranker's own order breaking what is left. Region is no part of that choice and it is no part of yours: a header mark and a footer mark are as often one mark as they are a light/dark pair, and only `home.png` can tell you which. Override the pre-selection when the screenshot shows it is the wrong mark or the wrong variant for an email header — and when you do, say in your report which row you took and what you saw. Two candidates that differ only in file format are not a preference: taking the one that needs converting is how a run shipped a mark the rasterizer then refused, with an email-safe capture of the same mark sitting beside it in the packet.

`svgPath` arrives **pre-filled** on the normal path: `homepage-pass.js` keeps the SVG markup the render already had — the bytes the browser downloaded for an `<img src="…logo.svg">`, and the serialized markup of a logo the site ships as **inline `<svg>`** in the document — and the scaffolder copies the reduced markup into `candidates.logos[].value.svgPath`. **Copy that value verbatim** into `brand.logos[]`. An empty `svgPath` on a RASTER logo (png/jpg/webp, or a favicon) is a valid, shipping outcome, not a gap to close — and for a non-email-safe raster URL the finalizer may still replace that `url` with a PNG it minted from the captured bytes, so read `finalize-report.json.logo_hosting` for what actually shipped.

**An inline-`<svg>` logo ships with `svgPath` filled and `url` empty.** There is no public URL for one — the mark is markup in the page, never a downloaded file — so its candidate carries `url: ""`, which the schema permits (`url` is a required KEY, not a required value). Copy the candidate verbatim, empty `url` included; do NOT substitute a favicon URL, an `og:image`, or a guessed `/logo.svg` to make the row look complete. (The finalizer is the ONE thing that may later write a `url` onto such a row, and only with a `.png` it minted from that capture's own bytes — it is not your edit to make.) Such a candidate ranks below a downloaded logo asset and **above a favicon** — a header logo is the brand mark, a favicon is a 32px stand-in. It also arrives with a **measured** `background` (`light`/`dark`, from the band the mark actually sits on) rather than the usual `"unknown"`; that is evidence, so keep it — the "override only with screenshot evidence" note above is about *your* choosing a value, not about discarding a measured one. The measurement is **best-effort, and `"unknown"` is its honest answer**, not a failure: the probe reads background *colours*, so a mark over a hero image or under a transparent overlay band reports `"unknown"` rather than guess. Treat a returned `"unknown"` exactly like any other unknown — do not "improve" it from the screenshot unless you genuinely can see which band the mark sits on.

**A captured `svgPath` is evidence of the mark and NOT an email-usable asset — unless the finalizer minted a hosted PNG this run.** `svgPath` holds the svg's INNER markup only, so the root element the capture worked to make correct (the synthesized `viewBox`, the `xmlns`) lives on solely in a worker-local technical sidecar that is never published; and nothing downstream converts the mark later — the reviewed consumer copies `brand.logos[].url` into an image `src` unchanged, and for an inline capture that url is empty. The finalizer is the one step that can close that gap while the sidecar bytes still exist: it uploads them, `upload_image` rasterizes server-side, and the returned hosted `.png` is written into the in-memory final brandkit. **On every other outcome the old truth stands verbatim** — a run that captured only inline logos has NOT given the user a logo they can put in an email, it has proved what the mark looks like. Read `finalize-report.json.logo_hosting` rather than assuming either way, report the matching line ([Logo outcome](#logo-outcome--a-missing-brand-logo-is-said-out-loud-not-footnoted)), and never treat a filled `svgPath` on its own as the gap being closed.

**Do NOT invoke `save-logo-asset.js` on the normal path.** It re-fetches the asset through the publisher browser proxy, which admits only the hosts this thread's egress grant covers — so a logo on a third-party CDN (a shop CDN, an image-transform CDN) is refused there and the invocation fails with an approval error you cannot satisfy. The bytes it would fetch have already been kept. `extract-svg-path.js` likewise only helps for a local `.svg` file you already have. Reach for either one only when a specific logo's `svgPath` is empty AND you have positive evidence it is an SVG the pass missed — and never use `save-logo-asset.js` output as a public `url`.

Same-mark substitution after a failed conversion is conservative dormant support for explicitly evidenced inputs. It requires nonblank matching alt, rendered size, and a known matching background band. The normal img collector does not measure that band: unknown-band candidates cannot trigger automatic recovery. Keep the source logo and report the refusal in that case.
