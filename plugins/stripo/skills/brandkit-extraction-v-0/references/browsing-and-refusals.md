# Browsing and refusals

Read this on any refused navigation, any `target_not_approved`, or any
`session_create_failed`. The contract's one-paragraph refusal rule is the
summary; this is the whole text.

**Browsing goes through the thread's browser session, and whether the target host is already reachable is not knowable before you try.** Two things can put a host on the session before your first turn: a browse grant some deployments derive from the domain named in the request and apply at dispatch, and any still-active `website_access` previously approved in this thread, which is loaded into later runs until it expires. A run starts without the host when neither supplied it — including a thread whose earlier approval has since lapsed, so a request that browsed freely yesterday can be refused today. All of that is ordinary, you cannot tell which happened from inside the run, and the first navigation is the test. Do NOT request `website_access` for the extraction target while browsing works: browsing is not something to negotiate, and asking for a grant you already hold stalls the run behind a Slack card nobody was expecting. A refused first navigation is not a fault to report either — it is expected and answerable, and the branches below say how. Use `PUBLISHER_BROWSER_PROXY_URL` as the Chromium/Playwright proxy; the control plane sets that variable on every turn regardless of what is granted, so neither its presence nor its absence carries any authorization signal — never read it as consent.

**A refused navigation is how a missing grant surfaces, and it is answerable — read the refusal the scripts hand you and act on it, once.** It arrives by one of two routes, decided by the browser this run was given rather than by anything you choose, and both mean the same thing. A Browserbase run is refused when it attempts to mint a session — the check runs before anything is created upstream — as an error whose `code` is exactly `target_not_approved` carrying the host as `host` (see the carve-out below). Local Chromium — and any direct fetch through the proxy — is refused at the tunnel (`ERR_TUNNEL_CONNECTION_FAILED`, a 403 from the proxy); there the vendored classifier (`scripts/lib/browser-proxy-refusal.js`) has already told the cases apart, so the refusal text is your instruction:

- **It names the `website_access` approval and the host to approve.** Ask a human for that approval, for exactly the host it names, then retry the navigation once. This is the platform's ordinary approval path, it still exists, and this refusal is the one situation in this skill that uses it.
- **It says the failure is NOT an approval problem** — a non-443 port, the proxy's own host policy, HTTP 407 credentials, a 502/504 from the far end, or a proxy that never answered. Those are a platform or configuration fault that asking cannot fix: stop and report it, naming the refused host and the refusal itself.

Either way, do not retry in a loop, do not fall back to direct network calls, and do not silently switch browser modes: at most one approval request per host and one retry after it, and if the same host is refused again, report it and stop. The same no-silent-fallback rule covers Browserbase: if a Browserbase session fails for an ordinary reason (HTTP 4xx, network, timeout), surface the error and stop — do NOT silently retry with local Chromium. There is one internal exception: the packaged `homepage-pass.js` may automatically replace a released, standard unproxied publisher-proxy session with exactly one residential session when conservative provider-specific live evidence marks the rendered page fallback-eligible and the proxy says the transition is available. The agent must not issue that retry itself. A homepage still blocked after that one internal attempt remains a legitimate terminal state.

**The one Browserbase carve-out from that stop rule is an error whose `code` is exactly `target_not_approved`.** It is the missing-grant case above, on the mint route rather than the tunnel: the run reached you with no host on its browser-proxy session, the proxy said so in a machine-readable field, and the error carries the host as `host`. Take the first branch above — ask a human for the `website_access` approval, for exactly that host, then retry once — under the same budget of one ask per host and one retry. **That code now has a second trigger, and the branch is the same for both:** a navigation refused DURING a run — a click or a page script that walked the browser onto a host this thread's session does not carry — raises the identical `code` and `host`, so a run that began fine can still end here. Handle it exactly as the mint case, with one difference: the retry restarts the extraction from the beginning, because an in-run refusal cannot resume (the browser session it happened in is already gone). **Every other Browserbase `code` stops the run**, and `session_create_failed` above all: it is a catch-all covering a bad API key, an exhausted quota, a proxy that never answered and any other non-2xx, so sending it to a human produces an approval card that cannot fix anything. Match the code exactly; never infer the branch from the HTTP status or from the prose.
